# Documentation and Tooling in eser/stack

Facts about the eser/stack repository that the documentation-conventions and
tooling-standards skills refer to.

## Where documents live

| Location                          | Holds                                                       |
| --------------------------------- | ----------------------------------------------------------- |
| `README.md`                       | Project overview, install, first run                        |
| `pkg/@eserstack/<name>/README.md` | Package usage                                               |
| `pkg/ajan/<name>/README.md`       | Go package usage (Go package READMEs below)                 |
| `.github/ARCHITECTURE.md`         | Architecture overview and the package dependency graph      |
| `.github/SECURITY.md`             | Security policy and reporting                               |
| `.github/CONTRIBUTING.md`         | Contributor setup and checks (setup: `pnpm cli init`)       |
| `docs/adr/`                       | Architectural decisions, named `NNNN-kebab-title.md`        |
| `docs/schema/`                    | JSON schemas, written by hand                               |
| `CHANGELOG.md`                    | Generated by `pnpm cli changelog` at release                |
| `TODOS.md`, `backlog/`            | Open work; backlog tasks are managed with the `backlog` CLI |

Install and first-run changes to noskills-server stay within the
time-to-hello-world target in `docs/adr/0002-magical-moment-and-tthw-target.md`.

## Go package READMEs

The ajan Go packages with a README (`clifx`, `configfx`, `connfx`, `formatfx`,
`httpclient`, `httpfx`, `i18nfx`, `lib`, `lib/netlib`, `logfx`, `processfx`,
`results` and `types` under `pkg/ajan/`) follow documentation-conventions: Package README Structure, with
Go in place of the TypeScript import pattern:

- The title is `# <emoji> [ajan/<name>](./)`.
- A blockquote under it gives the import path
  (`github.com/eser/stack/pkg/ajan/<name>`) and says the root module is not
  published for `go get` (languages-and-security.md: Go Modules and Layout).
- The Quick Start is a complete `package main` that runs inside this
  repository. Later blocks are fragments that compile with the Quick Start's
  imports and the variables they name; signature listings are marked with
  `// func ...` comments.
- The 🔗 Links footer starts with `go doc github.com/eser/stack/pkg/ajan/<name>`
  as the API reference and links the related ajan READMEs.

## API reference

There is no generated HTML API reference (decision-43). The JSDoc in each
package's source is the reference, and `pnpm cli docs-lint`
(`eser codebase validate-docs`) checks that exported symbols carry it.

## CLI-first packages

`ai`, `codebase`, `kit`, `noskills` and `workflows` map the `.` export to their
CLI `main.ts` (`node ./pkg/@eserstack/workflows/main.ts` starts the workflows
CLI). Each one publishes its library as `./mod`, which READMEs import as
`import * as workflows from "@eserstack/workflows/mod"`
(documentation-conventions: README Import Pattern), and its command tree as
`./module`, which `pkg/@eserstack/cli/main.ts` mounts in the `eser` CLI. The
`./mod` of `kit` holds only `moduleDef`; its recipe library is the `./recipes`
export.
`laroux-server` is not one of them: its `.` export is the server library
(`startServer`), and its CLI is the `./cli` export and the `laroux` npm binary.

## Platform packages and `type: module`

Every package's `package.json` sets `"type": "module"` except the six `ajan-*`
platform packages (`ajan-darwin-arm64`, `ajan-darwin-x64`, `ajan-linux-arm64`,
`ajan-linux-x64`, `ajan-win32-x64` and `ajan-wasm`) and the five `noskills-*`
binary packages (`noskills-darwin-arm64`, `noskills-darwin-x64`,
`noskills-linux-arm64`, `noskills-linux-x64` and `noskills-win32-x64`). This is
a deliberate exception. They ship no JavaScript, only a prebuilt shared library
with its C header (or, in `ajan-wasm`, the two WebAssembly modules) or the Go
`noskills` binary, and `type` only tells Node how to load `.js` files. They have
no `exports` either. They are published to npm only, where `@eserstack/ajan`
and the `eser` npm package list the `ajan-*` packages as
`optionalDependencies`, and the `noskills` npm package lists both sets.

## Dependency registries

Dependencies follow tooling-standards: Registry Preference. The decisions for
packages that exist on both registries:

- `yaml` comes from JSR as `@eemeli/yaml`, declared as
  `"@eemeli/yaml": "npm:@jsr/eemeli__yaml@^2.9.1"` in `codebase`, `config`,
  `formats`, `noskills` and `workflows`, and imported as `"@eemeli/yaml"`. Its
  author publishes stable releases to both registries.
- `openai` stays on npm in `ai`. OpenAI stopped publishing `@openai/openai` to
  JSR on 2026-07-30 (openai/openai-node#2037), so the JSR package ends at 7.2.0
  while npm keeps releasing (7.28.0 as of 2026-10-04). The JSR build also
  declares `@aws-sdk/credential-provider-node`, `@smithy/hash-node`,
  `@smithy/signature-v4` and `zod@3` as hard dependencies, which the npm package
  lists as optional peers. Move it to JSR if OpenAI publishes there again.

## File naming and license headers

`validate-filenames` in `.eser/manifest.yml` applies kebab-case to the whole
tree and snake_case under `cmd/`, `pkg/ajan/` and `pkg/@eserstack/ajan/`. Its
exclude list covers `.agents/` and `.claude/` (skill files are named
`SKILL.md`), `backlog/` (Backlog.md task file names), `.github/`, fixed names
such as `README.md`, `AGENTS.md`, `CHANGELOG.md`, `TODOS.md`, `Makefile`,
`Dockerfile` and `LICENSE`, and generated or scratch paths (`docs/`,
`etc/coverage/`, `etc/temp/`, `.eser/recipes/`).

Every `.ts`, `.tsx` and `.go` source file starts with this header;
`validate-licenses` checks it and skips `.eser/recipes/`:

```typescript
// Copyright 2023-present Eser Ozvataf and other contributors. All rights reserved. Apache-2.0 license.
```

The codebase is Apache-2.0, so a new dependency's license must be compatible
with it.

`third-party/` holds in-tree forks of other projects' code, which keep their
own file names, license headers and style so they can be rebased onto new
upstream versions. `validate-filenames`, `validate-licenses`, the EOF,
trailing-whitespace, BOM and line-ending validators, oxfmt and oxlint (the
`ignorePatterns` in `.oxfmtrc.json` and `.oxlintrc.json`) and golangci-lint
(`.golangci.yaml` exclusions) skip it, and
`validate-code-conventions` only reads JavaScript and TypeScript files, which it
has none of. Each fork has a `FORK.md`; the only one today is
`third-party/jsonschema/` (decision-56).

## Package scripts

The root `package.json` scripts (`check`, `lint`, `fmt`, `test`, `bench`,
`cli`, `laroux-cli`, `noskills-cli`) run as `pnpm <name>` or `node --run <name>`;
`cli`, `laroux-cli` and `noskills-cli` are the CLI entry points. Every other
command is a manifest script, run as `pnpm cli <name>`. `@eserstack/posts` is
the one package with `scripts` of its own (`tui`, `test`, `test:coverage`), run
from its directory with `node --run <name>`. The `package.json` scripts in `.eser/recipes/` belong to
the apps generated from them. The `npm install -g eser` and `npx eser` lines in
`README.md` are install instructions for users of the published CLI and stay.

## Package templates

`.eser/recipes/library-pkg/` is the template for a new `@eserstack/*` package
and `go-service/` for a Go service. The other recipes (`laroux-app/`,
`vanilla-app/`, `vite-app/`, `cf-workers-app/`, `fp-pipe/`) are app starters.
Recipes are excluded from lint and format by the `ignorePatterns` in
`.oxfmtrc.json` and `.oxlintrc.json`.

To add a package, copy `library-pkg/` to `pkg/@eserstack/<name>/` and replace
`package-name` in its `package.json` and README. Its `package.json` version is
`0.0.0`, and the next release sets it to the shared version. Then run
`pnpm install` at the root to link the package, `pnpm exec oxfmt` on it (the
rename changes the README's line breaks) and `pnpm cli ok`.
